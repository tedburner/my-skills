# 流程图语义类型选型与分层细则

本技能支持 6 种架构流程图语义类型。**图型只决定中间核心处理区如何分组**，所有图型都严格遵循统一的自上而下阅读方向与 5 段式纵向骨架：

1. `外部触发 / 入口`（统一使用“外部触发源”，不用“外部刺激”）
2. `接入适配 / 协议转换`
3. `核心处理 / 业务流程`
4. `出站适配 / 共享能力`
5. `数据、基础设施与外部系统`

---

## 一、选型决策表

根据仓库扫描得到的入口类型、核心单元、流程复杂度、代码组织和依赖形态选择唯一主图型：

| 流程图语义类型 | 典型适用项目 | 核心识别信号 | 核心处理区分组方式 |
|---|---|---|---|
| `服务分层型` | 完整后端应用、DDD 服务、业务平台 | Controller/MQ/Job 多类触发 + Domain/Application Service + DB/Cache/RPC | 按 3–5 个业务价值流领域横向并列 |
| `代码逻辑分层型` | Python/FastAPI/Triton、推理服务、算法引擎、清晰单体 | API Router -> Service -> Engine -> Core Inference，无需 DDD 包装 | 按真实代码职责层纵向堆叠（8–15 个关键节点） |
| `中间件处理链路型` | 网关、协议适配器、数据中心、数据组装/路由服务 | 多上游输入汇入，经归一、映射、组装、路由、规则后输出 | 按核心处理流水线阶段纵向推进（2–6 个模块） |
| `业务泳道型` | 端到端业务链路、可视化生成、训练/标注/评测、运营闭环 | 多角色/多子系统阶段流转，常带日志回流或离线训练旁路 | 按业务阶段分层，同层内并列责任方；旁路放底部/右下 |
| `组件/包逻辑型` | Maven/Gradle 多模块、`starter/provider/facade/common/core`、SDK/分词/索引 | 包与模块依赖边界清晰，存在词表/配置加载或定时刷新链路 | 按模块/包调用顺序自上而下排列，底部附说明区 |
| `双流程/状态机型` | RAG + Agent/Graph、同步查询链路与异步/流式状态机并存 | 同一入口下存在两条相对独立的主链路（如普通检索 vs 状态图编排） | 核心层左右并列两条纵向子流程，下方共享依赖与客户端 |

> 若用户提供了参考图：先提取其模块语义与调用关系，再重构为本技能统一的自上而下布局；原图中的左右主干或侧边栏一律转换为纵向分层、同层共享能力区或底部说明区。

---

## 二、各图型分层与内容规范

### 1. 服务分层型

使用 4 个（或含独立协议适配层共 5 个）左右边界对齐的主层级：

1. **触发器层 / 入口层（Inbound / Trigger Layer）**
   - 只按触发机制做粗粒度分类，至少区分实际存在的：`HTTP/RESTful API`、`Kafka 消费（或 MQ Consumer）`、`定时任务 / Job`，可选 `健康检查`、`内部 RPC`。
   - 不同入口类型在同一层级横向并列（禁止画成上下游），并用**虚线子框**物理隔离。
   - 保持克制：卡片只写入口类型与一句职责说明，**默认不枚举 Controller、Consumer、JobHandler 文件名**；仅当入口类自身承载核心编排逻辑或用户明确要求时，才在小字放 1 个代表类名。
2. **业务领域层（Domain / Service Layer）**
   - 按**业务价值流**划分为 3–5 个核心业务域，不要机械照搬代码包名（例如将散落的 `eval`、`report`、`task` 包提炼为业务读者一眼能懂的领域中文名）。
   - **领域卡片固定四要素**：
     - 第一行：领域中文名
     - 第二行：一句中文职责说明
     - 第三行：1–3 个代表代码定位线索（优先 `ApplicationService` / `DomainService` / `Engine` / `Processor` 类名或关键短名，推荐 2 个）
     - 底部：2–4 个关键能力小卡片
   - **严禁做成目录清单**：不展示完整子域列表（禁止底部拼 `子域：a - b - c`）、不列全量服务类或包名、不写“50+ 应用服务 / 30+ 仓储接口”等统计数字。能力过多时优先合并同类域、删减边缘能力。
3. **数据访问与底层适配层（Infrastructure / Outbound Adapters）**
   - 只列出站适配类别与代表关键字：`持久化适配（Mapper/Repository）`、`外部调用适配（统一归拢 OpenFeign/OkHttp/RestTemplate/WebClient）`、`消息出站（MQ Producer）`，不逐个展开全部 Mapper 或 Feign 接口。
   - VO / DTO / Assembler 不单独画到底层；如需提及，仅说明其内聚在 API 与 Service 交互边界。
4. **基础设施与外部系统（Infrastructure & External Services）**
   - 必须用虚线框明确区分 **`基础设施（Infrastructure）`**（如 MySQL、MongoDB、Redis、Kafka）与 **`外部系统依赖（External Services）`**。
   - 外部 RPC 下游默认聚合为 `外部系统依赖`，除非用户明确要求逐一展开。

### 2. 代码逻辑分层型

适用于 Python/FastAPI/Triton、算法引擎与模型推理服务，不强行套用 DDD 概念：

- **纵向主层级**：按真实职责堆叠，如 `入口层（Entry） -> 业务逻辑层（Business Logic） -> 引擎层（Engine） -> 核心推理层（Core Inference） -> 外部服务（External）`。
- **节点粒度**：全图精选对主链路最有解释价值的 **8–15 个关键文件/类/引擎**，每个节点必须带中文职责（如 `server.py API 路由`、`RecallEngine 召回引擎`），禁止纯英文类名堆叠。
- **横切公共能力**：`Common / 配置 / 工具 / 异常处理 / 模型元数据` 放在核心处理同层侧边辅助框或核心层下方的共享能力区，用虚线表达依赖注入、配置读取或初始化注册，不破坏主流程纵向动线。
- **底层物理依赖**：使用圆柱体或浅色块表达服务注册、监控指标、模型存储或推理后端。

---

### 3. 中间件处理链路型

适用于网关、适配器、数据路由与组装中心：

- **纵向结构**：`上游输入 -> 接入/协议适配 -> 核心中间件处理 -> 输出封装/下游接口 -> 内部配置与存储`。
- **上游与运营输入**：多个上游调用源在顶部入口层横向并列后汇入接入适配；管理后台、规则配置或人工运营入口放在顶部入口层或共享配置区，禁止画成从右向左插入主干。
- **核心处理区**：用 2–6 个模块表达关键处理阶段（如输入归一、字段映射、数据组装、路由分发、规则执行、结果封装）；单一简单链路可直接收敛为 `输入 -> 核心处理 -> 输出 -> 存储/依赖`。
- **底层支撑**：数据库、缓存、消息队列与内部配置放底部，可用虚线框区分 `配置管理` 与 `数据存储`。

---

### 4. 业务泳道型

适用于端到端业务流转、页面生成、模型训练/标注/评测与多角色运营闭环：

- **纵向阶段泳道**：每一阶段为一层水平泳道，整体从上到下推进（如 `触发与业务场景 -> 核心处理/生成服务 -> 结果页/交付服务`），同层内可横向并列不同责任组件。
- **业务化命名**：每个泳道具备中文标题与职责说明，内部步骤使用简短中文动词短语表达业务动作，禁止直接把代码包名当流程步骤。
- **旁路与闭环链路**：日志采集、离线标注训练、模型评测、数据回流等异步闭环能力放在主流程下方或右下角旁路区，使用虚线或区分底色连接主流程关键节点。

---

### 5. 组件/包逻辑型

适用于 Maven/Gradle 多模块、`starter/provider/facade/common/core-model`、分词/索引/规则引擎与 SDK 仓库：

- **纵向调用序排列**：按模块/包边界与主调用方向自上而下排列（如 `服务入口与调度 -> 业务服务层 -> 核心算法/引擎模型 -> 公共工具 / API 模型 -> 存储与外部系统`），不使用左到右主流程。
- **包块容量限制**：每个组件大框必须附中文职责标题；内部可列关键类/方法摘要，但**单块不超过 6 条**。
- **底部说明区**：配置文件、定时刷新链路、词典/模型数据结构、外部存储说明与图例统一收入底部或右下角说明区，避免塞爆主流程卡片。
- **线型区分**：主调用链用实线；配置加载、词表/缓存刷新、初始化注册用虚线。

---

### 6. 双流程/状态机型

适用于普通同步检索链路与异步/流式 Agent 状态图链路并存的服务：

- **顶层入口**：客户端与 Controller/Router 层置顶（可横跨两条流程上方）。
- **核心双列并排**：中间核心处理区左右并列两条独立容器（如左侧 `RAG 搜索业务流`、右侧 `Deep Research 状态图引擎`），各自配独立标题与主色调；每条流程内部节点（如 `Planner -> Search -> Evaluate -> Report`）严格自上而下排列，尽量各自闭环、减少跨列穿插。
- **共享底座**：LLM 客户端、配置中心、Redis/Nacos、外部模型与检索服务统一放在两条流程下方，使用**中性色**表达共享属性，避免误导为某条链路独占。
- **强制图例**：图例必须清晰说明两条主流程的颜色语义、实线/虚线含义以及中性色共享模块语义。
