# Repo Architecture Flow

使用本技能把代码仓库转换为稳定、可维护的流程架构图。最终必须生成：

- `.svg` 图片：用于直接预览、文档展示、手动上传 Confluence。
- `.drawio` 源文件：用于 diagrams.net 或 Confluence draw.io 插件中继续编辑。

如果用户额外要求 HTML 预览，可以在 SVG 与 drawio 之后再生成。HTML 只是预览或导出辅助，不作为后续维护的源文件。

## 工作流程

0. 命令与跨平台执行策略。
   - 不要强制统一使用 `bash`。macOS/Linux 通常有 bash 或 zsh，但 Windows 默认是 PowerShell；除非明确处于 Git Bash、WSL、MSYS2 或 bash 可用环境，否则 bash 命令不保证可执行。
   - 核心采集逻辑优先放在 Python 标准库脚本中，例如 `scripts/collect_architecture_facts.py`；这样 Windows、macOS、Linux 都能运行，shell 只负责启动脚本。
   - 文档中的命令示例优先写成跨平台 Python 调用：`python <skill-dir>/scripts/collect_architecture_facts.py --root <repo-root>`。
   - 需要文件搜索时优先使用 `rg --files`；如果不可用，再按当前 shell 选择替代：
     - PowerShell / Windows：`Get-ChildItem -Recurse`、`Select-String`。
     - bash/zsh / macOS/Linux：`find`、`grep`。
   - 避免在通用步骤中使用 bash 专属语法，例如 here-doc、`$(...)`、`>` 重定向组合、`xargs` 管道或 `$HOME` 默认展开；如果必须使用，必须同时给出 PowerShell 等价命令。
   - Windows 路径和 macOS/Linux 路径示例要分开写，不要假设 `/`、`~`、环境变量和转义规则完全一致。

1. 先扫描仓库，再绘图。
   - 优先使用 `rg --files`；如果遇到权限拒绝或不可用，按当前 shell 使用 `Get-ChildItem`、`find` 等替代命令。
   - 阅读项目指导文件，例如 `AGENTS.md`、`CLAUDE.md`、README、构建文件、主配置文件。
   - Java/Spring 项目重点检查 `interfaces`、`domain`、`application`、`infrastructure` 等包。

2. 收集架构证据。
   - 对 Java/Spring 或类似结构项目，运行事实采集脚本。
   - 如果技能在项目内：`python .agents/skills/repo-architecture-flow/scripts/collect_architecture_facts.py --root .`
   - 如果技能在全局目录：`python <skill-dir>/scripts/collect_architecture_facts.py --root <repo-root>`
   - 该脚本只依赖 Python 标准库，适用于 Windows、macOS、Linux。
   - 脚本输出只作为证据，不直接等同于最终架构模型。
   - 对包名容易误导、服务类过大、模块边界不清的地方，要继续人工阅读关键文件。

3. 如果已有架构图，先读取现有产物。
   - 如果存在 `.drawio`，优先把它作为源文件参考，尽量保留整体布局、层级顺序、配色和命名风格。
   - 如果只存在 `.svg` 或 `.html`，把它作为视觉参考，但重新生成 `.drawio` 时必须使用可编辑 mxGraph 单元格。
   - 除非用户要求重绘，否则不要让布局大幅漂移；优先做增量更新和命名修正。

4. 先判断流程图语义类型，但所有类型都使用统一的自上而下布局。
   - 统一方向：从上到下阅读，顶部是外部触发/入口，中间是核心处理，底部是数据、基础设施和外部系统。
   - 统一结构：每张图都尽量组织为 `触发入口 -> 协议/适配 -> 核心处理 -> 出站适配 -> 数据与外部依赖`。图型只决定中间核心处理如何分组。
   - `服务分层型`：适用于完整后端应用、DDD 服务、平台服务。核心处理按业务领域分组。
   - `代码逻辑分层型`：适用于推理服务、算法服务、Python/FastAPI 服务、模块清晰的单体服务。核心处理按入口、业务逻辑、引擎、核心推理分层。
   - `中间件处理链路型`：适用于中间件、数据中心、网关、适配器、数据组装服务。核心处理按输入归一、转换/组装、路由/规则、输出封装分层。
   - `业务泳道型`：适用于业务流程、可视化生成、模型训练/标注/评测、运营链路。核心处理按业务阶段或责任泳道分组，但整体仍从上到下推进。
   - `组件/包逻辑型`：适用于 Java 多模块、starter/provider/facade/common/core-model 这类包结构清晰的项目。核心处理按包/组件分组，并按调用顺序自上而下排列。
   - `双流程/状态机型`：适用于同时存在两条主链路的服务，例如普通 RAG 搜索链路与 Deep Research 状态图链路。两条流程在同一层内左右并列，但每条流程内部仍自上而下。
   - 如果用户给了参考图，优先理解参考图的结构语义，再转换为本技能统一的自上而下风格；不要照搬参考图的左右拓扑或任意线条走向。

5. 用项目字段选择流程图语义类型。
   - `入口类型`：HTTP/CLI/MQ/Job/SDK/Controller/API Router。
   - `核心单元`：Domain Service、Engine、Pipeline、Graph Node、Provider、Processor、Adapter、Scheduler。
   - `流程复杂度`：单主链路、多阶段链路、双主链路、状态机、旁路训练/刷新。
   - `代码组织`：DDD 分层、Python 模块、Java package/module、starter/provider/facade、脚本型项目。
   - `依赖形态`：DB/Cache/MQ/RPC/模型服务/配置中心/指标监控/文件或词典。
   - 选择规则：
     - DDD 或完整业务平台 -> `服务分层型`。
     - FastAPI/Triton/模型推理/算法引擎 -> `代码逻辑分层型`。
     - 网关/适配器/数据组装/中间件 -> `中间件处理链路型`。
     - 页面生成/训练标注/运营闭环/多角色协作 -> `业务泳道型`。
     - Java 多包边界清晰、Provider/Core/Common/Facade 明显 -> `组件/包逻辑型`。
     - RAG/Agent/Graph/普通链路和状态机链路并存 -> `双流程/状态机型`。
   - 类型选择用于决定核心处理区怎么分组，不改变统一的自上而下布局。

6. 参考图模式库，转换为统一自上而下风格。
   - `推理/算法服务代码逻辑分层图`：
     - 自上而下排列：入口层、业务逻辑层、引擎层、核心推理层、外部服务层。
     - `公共模块（Common）` 不再固定右侧；统一放在核心处理旁的同层辅助区或核心处理下方的共享能力区，避免破坏主流程方向。
     - 实线表示主调用链，虚线表示依赖注入、内部引用、配置读取或初始化注册。
     - 适合 Python/FastAPI/Triton/模型推理服务，不要强行抽象成 DDD 领域层。
   - `Java 组件/包逻辑图`：
     - 按调用顺序自上而下排列包或组件边界，例如 `SYS-Server -> Provider -> Core Model -> Common/Facade -> 存储/外部系统`。
     - 入口模块、Controller、Scheduler、配置文件放上层；业务服务放中层；核心算法/模型/数据结构放下层；公共工具和 API 模型放共享能力区。
     - 图例、词表/配置说明、调度刷新流程、外部存储说明统一放在底部说明区或右下角小图例，不抢主流程视觉中心。
     - 适合分词、索引、规则引擎、SDK/provider 类项目。
   - `双流程/状态机架构图`：
     - 顶部放客户端和 Controller 层。
     - 中间并列放两条核心流程，例如 `RAG Search 业务层` 与 `Deep Research 状态图引擎`；两条流程内部都从上到下排列节点。
     - 下方放共享客户端、配置与基础设施、外部服务依赖。
     - 用颜色区分不同流程，图例必须说明颜色含义；共享模块使用中性色或单独容器。
     - 适合同时有同步搜索链路、异步/流式状态机、Agent/Graph 节点编排的项目。

7. 如果选择 `服务分层型`，再识别分层。
   - 触发器层 / 入口层：只做粗粒度入口分类，例如 `HTTP/RESTful API`、`Kafka 消费`、`定时任务/Job`、`健康检查`、`内部 RPC`。它们属于同一层级，但要用虚线框物理隔离不同入口类型。
   - 入口层不要枚举每个 Controller、Consumer 或 Job 文件名；除非入口本身就是项目核心能力，入口卡片只写入口类型和一句职责说明。
   - 业务领域层：按业务价值流划分领域，每个领域必须有中文名称、一句中文职责说明，以及可定位到代码的代表类名或关键短名。
   - 领域内部只展示重要能力点，不展示完整子域、包名或服务类清单；默认每个领域展示 2-4 个关键能力即可。
   - 数据访问与底层适配层：持久化适配、外部调用适配、MQ Producer 等业务层向下的出站适配。
   - 基础设施与外部系统层：只放边界外系统或中间件，并用虚线框区分基础设施和外部系统依赖。

8. 如果选择 `代码逻辑分层型`，按以下方式组织。
   - 主体按层级纵向堆叠，层名可以来自代码真实职责，例如 `入口层（Entry）`、`业务逻辑层（Business Logic）`、`引擎层（Engine）`、`核心推理层（Core Inference）`、`外部服务（External）`。
   - 每层内部放关键文件、类或引擎，但必须附中文功能说明，例如 `server.py API路由`、`RecallEngine 召回引擎`。
   - 公共模块、配置、工具、异常处理、模型元数据等横切依赖放在同层共享能力区或核心处理下方；连线以虚线为主。
   - 外部服务和物理依赖放底部，使用圆柱或浅色块表达服务注册、指标监控、推理后端等。
   - 不要把所有 `.py` 或 `.java` 文件都放入图中，只选择对主链路有解释价值的 8-15 个节点。

9. 如果选择 `中间件处理链路型`，按以下方式组织。
   - 自上而下排列为：上游输入 -> 接入/协议适配 -> 核心中间件处理 -> 输出封装/下游接口 -> 内部配置与存储。
   - 核心中间件处理内部用 2-6 个模块表达核心功能，例如数据组装、字段映射、协议适配、路由、规则执行、结果封装。
   - 多个上游来源放在顶部同一入口层内，用并列卡片表示，再汇入统一输入适配。
   - 管理平台、配置输入、人工运营入口放在入口层或共享配置区，不画成从右向左进入。
   - 内部配置、缓存、消息队列、数据库等物理依赖放底部，配置与存储可以用虚线框分区。
   - 如果只有一个核心流程，就画成简单的 `输入 -> 核心处理 -> 输出 -> 存储/依赖`。

10. 如果选择 `业务泳道型`，按以下方式组织。
   - 泳道仍统一自上而下：每个阶段是一层，每层内可以并列展示不同责任方或组件。
   - 阶段适合表达端到端业务链路，例如业务场景、生成服务、结果页服务、组件库、模型生成服务。
   - 旁路能力，例如日志采集、标注训练、模型评测、数据回流，放在主流程下方或右下角旁路区，用虚线连接主流程关键节点。
   - 每个泳道都要有中文标题和职责说明，步骤用简短动词短语表达。
   - 对训练、评测、部署、数据回流这类闭环流程，用虚线或不同底色表示旁路/异步链路。
   - 不要把代码包名直接画成流程步骤；应抽象成用户或系统能理解的业务动作。

11. 如果选择 `组件/包逻辑型`，按以下方式组织。
   - 优先按 Maven/Gradle module、Java package、Python package、npm package 或清晰目录边界分组。
   - 每个大包块都必须有中文职责，例如 `服务入口与调度`、`业务服务层`、`分词引擎核心`、`公共工具`、`API 模型`。
   - 包/组件按调用方向自上而下排列，不使用左到右主流程。
   - 组件内部可以放关键类/方法摘要，但一个块内不超过 6 个条目；过多条目放到说明区。
   - 说明区适合放图例、配置文件、调度刷新链路、词典/模型数据结构、外部存储说明，优先放底部或右下角。
   - 调用主线使用实线，配置加载、数据刷新、初始化注册使用虚线或浅色线。

12. 如果选择 `双流程/状态机型`，按以下方式组织。
   - 两条主流程在核心处理层内左右并列，每条流程有独立标题和颜色，例如 `RAG 搜索流程`、`Deep Research 状态图流程`。
   - Controller 或入口层可以横跨两条流程，但进入流程后应尽量各自闭环，避免线条来回穿插。
   - 状态图、Planner、Search、Info、Report 等节点按执行顺序自上而下排列；普通业务服务按调用链自上而下排列。
   - 共享依赖放在两条流程下方，如 LLM 客户端、配置管理、Redis/Nacos、外部模型服务。
   - 图例必须说明颜色、实线/虚线和共享模块含义。

13. 抽象业务领域或核心能力。
   - 不要机械照搬包名，除非包名已经准确表达业务边界。
   - 优先按价值流划分。对于 query-quality 类平台，默认使用以下抽象，除非扫描证据明显不支持：
     - `质量评测域`：负责产生质检数据，是核心高价值资产来源。
     - `度量看板域`：负责消费并展示质检数据，支撑监控、告警、统计。
     - `任务管理域`：负责质检生命周期控制，包括 PK 任务、版本、调度、进度。
   - 每个模块都要有中文功能说明，不要只放类名。
   - 不要默认在领域卡片中展示 `子域`、`包`、`module`、`subpackage` 这类完整清单；它们通常是代码目录信息，不是架构主信息。
   - 如果扫描到大量子域或服务类，只选择能解释主业务流的关键能力。其余信息放到采集事实、附录或不展示。
   - 领域卡片推荐结构：
     - 第一行：领域中文名。
     - 第二行：一句职责说明。
     - 第三行：1-3 个代表代码线索。
     - 底部：2-4 个关键能力小卡片。
   - 如果领域数量或能力点过多，优先合并同类领域、删减边缘能力，不要增加叠层或把卡片挤成目录页。

14. 过滤非核心部署与运行时信息。
   - 架构流程图默认表达“代码逻辑与业务流转”，不是部署拓扑图。
   - Docker、K8s、JVM 参数、GC、健康探针、CI/CD、SpotBugs、Gradle 任务、端口、容器镜像等部署/运行时信息，默认不要放入主图。
   - 只有当项目核心能力本身就是部署、运维、调度平台、网关治理、运行时编排，或用户明确要求展示部署视角时，才可以增加 `部署与运行时` 区域。
   - Spring Boot、Java 版本、框架版本等可作为页脚小字或事实说明，不作为主层级。

15. 代码定位线索。
   - 代码定位线索优先放在业务领域层、核心处理层、组件/包核心块中，而不是放在入口层。
   - 每个业务域或核心处理块必须带 1-3 个代码定位线索，优先选择 Application Service、Domain Service、Engine、Processor、Provider 等真正承载业务逻辑的类名或关键短名。
   - 入口层只保留粗粒度入口类型，例如 `HTTP/RESTful`、`Kafka Consumer`、`XXL-Job`；默认不要列出每个 Controller、Consumer、JobHandler 文件名。
   - 只有当 Controller/Consumer/JobHandler 本身承载了明显业务编排逻辑，或者用户明确要求入口可定位时，才可以把 1 个代表入口类名放到入口层的小字中。
   - 代码线索放在领域或核心模块副标题/第二行小字中，例如 `RiskDashboardServiceImpl / MonitorDashboardServiceImpl`，可以只保留关键单词，但必须能帮助读者回到代码。
   - 不要把所有文件都塞进图里；每个业务域最多列 3 个最能代表核心逻辑的名称，推荐 2 个。
   - 不要在领域卡片底部增加 `子域：xxx - yyy - zzz` 这类长文本；这类信息会制造遮挡和叠层，默认删除。
   - 出站适配层只列适配类型和代表关键字，例如 `Mapper/Repository`、`OpenFeign Client`、`Kafka Producer`，不要展开所有 Mapper 或 Feign 类。

16. 统一绘图原则。
   - 所有主层级外框保持相同左右边界。
   - 所有架构流程图统一自上而下布局；禁止使用左侧输入、右侧输出、上方输出、中心发散这类不一致的主阅读方向。
   - 同一层内部可以左右并列模块，但层与层之间只能从上向下推进。
   - 同层不同入口类型使用虚线子框隔离。
   - 尽量减少交叉箭头，优先使用纵向箭头或总线式连线。
   - 连线默认只允许三种形态：垂直直线、水平直线、直角折线。禁止使用斜线作为主流程或跨层调用线。
   - 跨层连线必须走层间空白通道；不要在入口虚线框内部画横线，也不要让线条穿过模块卡片、标题或说明文字。
   - 如果入口到领域存在一对多关系，优先用少量代表性纵向箭头表达主流向，或使用层间总线说明“按请求/消息/调度分发”；不要为了穷尽调用关系画出大面积 fan-out。
   - 连接线必须作为背景层绘制：SVG 中先画线再画卡片；drawio 中 edge `mxCell` 要排在 vertex `mxCell` 之前，确保卡片和文字在视觉上盖在线条之上。
   - 如果某条线不能同时满足“走空白通道”和“背景层不遮挡”，就删除该线，改用层级说明或少量主箭头表达流向。
   - Feign、OkHttp、RestTemplate、WebClient 等统一归入 `外部调用适配`。
   - 外部 RPC 系统默认统一画成 `外部系统依赖`，不要逐个列出，除非用户明确要求。
   - 不要把 VO/DTO/Assembler 单独画到底层；如需表达，只说明它们内聚在 API 与 Service 的交互边界。
   - 最上层统一使用 `外部触发源`，不要使用 `外部刺激`。
   - 领域层建议控制在 3-5 个核心业务域，避免把每个包都画成一个领域。
   - 参考图中出现侧栏时，转换为统一的共享能力区、底部说明区或右下角图例，不承载主流程；主流程必须从上到下读通。
   - 图例要解释颜色、线型和区域语义；颜色不要只用于装饰。
   - 对代码逻辑图，类名/文件名可以出现，但必须配中文职责；不要只有英文类名堆叠。
   - 领域层不是服务目录页。不要展示领域服务数量、仓储接口数量、完整服务列表、完整子域列表或“50+ 应用服务”这类统计，除非用户明确要求盘点。

17. 生成产物。
   - SVG 默认输出到 `docs/architecture/<project>-flow-architecture.svg`，除非用户指定路径。
   - drawio 默认输出到 `docs/architecture/<project>-flow-architecture.drawio`。
   - drawio 必须可编辑：使用原生 mxGraph 图形、文本和连接线，不能只嵌入一张图片。
   - SVG 与 drawio 必须表达同一套层级、同一批模块、同一套命名；不要出现 SVG 是新版而 drawio 还是旧版的情况。
   - 如同时生成 HTML，HTML 可以引用或内嵌 SVG，但不要替代 `.drawio` 源文件。

18. 文案遮挡自检与修复。
   - 生成 SVG 和 drawio 后，必须进行一次“文案遮挡自检”，不能只检查 XML 合法性。
   - 自检对象包括：标题条、说明文本、领域卡片、子能力卡片、图例、连线标签、箭头标签。
   - 对每个文本节点估算最小占用空间：
     - 中文按约 `fontSize` 宽度估算，英文/数字按 `fontSize * 0.6` 估算。
     - 按文本框宽度计算预计行数；预计高度必须小于文本框高度减去上下内边距。
     - 单个卡片内正文超过 3 行，领域说明超过 2 行，图例超过 2 行时，必须缩短文案或扩大卡片。
   - 对每个容器检查内部元素是否重叠：
     - 子卡片必须全部落在容器内部，且不压住标题条和说明区。
     - 子卡片之间至少保留横向 18、纵向 14 的间距。
     - 标题条、说明文本和第一行子卡片不能共用同一 y 区间。
   - 对每条连线和连线标签检查是否穿过文字区域：
     - 主链路只允许经过层间空白带或卡片边界外侧。
     - 连线标签必须放在线段旁边的空白处，不能放在模块标题、说明文字或卡片正文上方。
   - 发现遮挡风险时必须先修复再交付，修复优先级：
     - 先缩短文案，删除非核心能力点、子域清单和统计数字。
     - 再增加卡片宽高、层高或层间距。
     - 再改为两行网格、总线式连线或减少代表性箭头。
     - 最后才降低字号；正文不得低于 10，标题不得低于 12。
   - 如果无法可靠视觉渲染 SVG/drawio，也要做几何自检：解析 drawio 的 `mxGeometry` 和 SVG 的 `x/y/width/height`，检查矩形重叠、文本框容量和边线穿越风险。
   - 最终回复中必须说明做了哪些校验；如果没有进行浏览器或 diagrams.net 视觉检查，要明确说明只做了 XML/几何自检。

## 输出规范

每张最终架构图必须包含：

- 项目或服务名称作为标题。
- 与所选语义类型匹配的核心处理分组，但整体必须统一自上而下。
- 所有图默认包含这些纵向区域，名称可按项目语义调整：
  - `1. 外部触发 / 入口`
  - `2. 接入适配 / 协议转换`
  - `3. 核心处理 / 业务流程`
  - `4. 出站适配 / 共享能力`
  - `5. 数据、基础设施与外部系统`
- 如果选择 `服务分层型`，可以使用四个或五个对齐的主层级：
  - `1. 触发器层 / 入口层（Inbound / Trigger Layer）`
  - `2. 业务领域层（Domain / Service Layer）`
  - `3. 数据访问与底层适配层（Infrastructure / Outbound Adapters）`
  - `4. 基础设施与外部系统（Infrastructure & External Services）`
- 如果选择 `代码逻辑分层型`，至少包含：
  - 入口层、业务逻辑层、引擎或核心处理层、外部服务或物理依赖层。
  - 公共模块或横切能力区。
  - 主调用链和配置/依赖虚线链路。
- 如果选择 `中间件处理链路型`，至少包含：
  - 上游输入或外部调用来源。
  - 接入适配、核心转换/组装、输出封装。
  - 对外输出接口或下游应用。
  - 内部配置、缓存、消息、数据库等支撑能力。
- 如果选择 `业务泳道型`，至少包含：
  - 业务场景或触发入口泳道。
  - 核心处理流程泳道。
  - 结果输出或页面服务泳道。
  - 可选的旁路数据、模型训练、日志采集或评测链路。
- 如果选择 `组件/包逻辑型`，至少包含：
  - 主要 package/module 分组。
  - 各组件中文职责。
  - 主调用链、配置加载链路、数据刷新或初始化链路。
  - 图例或说明区。
- 如果选择 `双流程/状态机型`，至少包含：
  - 两条并列主流程。
  - 共享客户端、配置和外部依赖区。
  - 颜色与线型图例。
- 每个业务域、核心能力、流程步骤和模块都要有中文标签或中文职责说明。
- 每个业务域只展示关键能力，不要求完整列出所有能力；默认每个领域 2-4 个能力点、1-3 个代码线索。
- 服务分层型的入口层中至少区分：
  - `HTTP/RESTful API`
  - `Kafka 消费`
  - `定时任务 / Job`
  - 可选：`健康检查`、`内部 RPC`
- 服务分层型的入口层卡片保持粗粒度，不默认展示 Controller/Consumer/Job 文件名；代码定位线索主要出现在业务领域层。
- 服务分层型的底层中必须区分：
  - `基础设施（Infrastructure）`
  - `外部系统依赖（External Services）`
- 同时生成 `.svg` 与 `.drawio` 两份文件。

## Draw.io 生成要求

`.drawio` 文件使用 XML 格式，包含 `<mxfile>`、`<diagram>`、`<mxGraphModel>`。

图形约定：

- 主层级外框：浅色圆角矩形。
- 子分组边界：虚线圆角矩形。
- 普通模块：圆角矩形。
- 存储组件：可使用 cylinder 形状。
- 共享能力/说明区：使用独立浅色大框，内部纵向或网格排列小卡片；优先放在核心处理下方或右下角，不作为主流程侧栏。
- 包/组件分组：使用带标题条的大框，标题中可以保留英文包名，但必须附中文职责。
- 图例：放在右上、左上或右下角的小框内，解释颜色、实线、虚线、内部调用、外部依赖等含义。
- 连接线：使用 `endArrow=block;html=1;rounded=0;`。
- 连接线必须保持正交风格：只使用垂直、水平或 90 度折线；默认禁止斜线。斜线会让架构图显得杂乱，除非用户明确要求，不能用于主调用链、跨层调用链或依赖线。
- SVG 连接线优先使用：
  - 垂直线：`M x1 y1 L x1 y2`。
  - 水平线：`M x1 y1 L x2 y1`。
  - 直角折线：`M x1 y1 L x1 yMid L x2 yMid L x2 y2`，或使用 `V/H` 命令。
  - 不要生成 `M x1 y1 L x2 y2` 这种 x/y 同时变化的斜线，除非它只是非常短的装饰性标记。
- drawio 连接线必须使用 `edgeStyle=orthogonalEdgeStyle;orthogonalLoop=1;jettySize=auto;html=1;rounded=0;`，并在跨列或跨层时显式设置 `mxPoint` 折点，避免 diagrams.net 自动路由成斜线。
- 有子模块的容器不要直接在容器 `value` 里写大段文字；应拆成：
  - 空白容器外框。
  - 顶部标题条。
  - 独立说明文本。
  - 子模块卡片。
- 容器、标题条、说明文本、子卡片必须使用固定网格布局：
  - 每个主层级预留独立标题条高度 28-34。
  - 标题条下方至少留 18-24 的说明文字区。
  - 说明文字区与第一行子卡片至少间隔 18。
  - 子卡片之间横向间隔至少 22，纵向间隔至少 18。
  - 业务域容器高度必须按“标题 + 说明 + 子卡片行数 + 内边距”计算，不允许靠自动换行挤压。
- 模块卡片文字控制在三行以内：第一行中文模块名，第二行代码线索，第三行职责摘要；如果放不下，缩短代码线索而不是缩小到不可读字号。
- 业务领域容器内部避免叠层：不要在一个领域容器内再放多个大容器；只允许放少量小能力卡片。需要二级分组时，最多使用一行小标签，不画成嵌套大框。
- 领域卡片高度不足时，优先减少能力点和代码线索，而不是增加重叠文本或缩小字号。
- drawio 容器文字默认容易居中覆盖子模块；如必须在容器上写文字，设置 `verticalAlign=top`、`spacingTop`，并预留足够顶部空间。
- 连接线不要从模块内部斜穿文字；优先使用层间总线、直角线、短垂直线。
- 如果发现连线需要斜着连接两个模块，先调整模块对齐或增加层间总线；仍无法避免时，删除该线并改用文字说明或代表性主箭头。
- 层间连线优先从上一层模块或分组底边出发，落到下一层模块或分组顶边；不要从大容器中心自动路由。
- 对跨列连接线设置明确折点，例如：先垂直到层间空白区，再水平移动，再垂直到目标边界。不要依赖 drawio 自动路由决定穿过哪个模块。
- 当 drawio 中 `edgeStyle=orthogonalEdgeStyle` 仍会穿过卡片时，必须改用显式 `mxPoint` 折点，或者减少为代表性主箭头。
- drawio 文件中连接线的 `mxCell` 必须放在对应模块卡片之前，作为底层线条；不要把所有 edge 放在 XML 末尾，否则 diagrams.net 会把线画在卡片和文字上方。
- 连线端点只允许落在分组或模块的外边界，不要落到模块中心；从模块中心出发通常会造成线条穿过内部文字。
- 主调用链用实线；配置读取、依赖注入、初始化注册、数据刷新、旁路训练/评测用虚线。
- 双流程图使用不同颜色表达不同主流程，但共享模块和外部依赖使用中性色，避免误导成某条流程独占。
- 主流程连线方向必须整体向下；允许在同层内短横向连接，但不允许形成左到右主阅读方向。

尽量使用稳定、可读的 ID，例如 `layer-inbound`、`domain-quality`、`adapter-rpc`。

## 视觉验收标准

生成前后都要按以下标准自检：

- 主层级外框左右边界一致，整体方正。
- 语义类型选择合理：完整服务优先服务分层型；推理/算法服务优先代码逻辑分层型；中间件/数据中心优先中间件处理链路型；复杂业务链路/模型流程优先业务泳道型；包结构清晰的组件库或 provider 优先组件/包逻辑型；双链路 Agent/RAG 服务优先双流程/状态机型。
- 所有语义类型都必须自上而下阅读，不能出现左侧输入、右侧输出、中心发散作为主流程。
- 入口类型在同一入口层并列展示，不要画成上下游关系。
- 不同入口类型必须有物理隔离，例如虚线框或分组标题。
- 入口层必须克制：只展示入口协议/触发类型和简短职责，不把每个 Controller、Consumer、Job 展开成卡片或小字列表。
- 核心处理层每个业务域、组件、引擎、泳道或状态流程都有中文名称和中文职责说明。
- 业务领域层每个领域必须有可定位代码线索，优先标 Service/Engine/Processor 类名或关键短名；不要把入口类名当作领域定位的主要依据。
- 业务领域层必须保持摘要级表达：不要完整列出所有子域、所有服务类、所有包名或数量统计；如果一张图开始像目录清单，必须删减到关键能力。
- 出站适配层只表达适配类型，不堆叠每个 Mapper、Feign、Producer 或工具类。
- 底层必须区分 `基础设施` 与 `外部系统依赖`，外部依赖默认聚合。
- 中间件处理链路型中，核心中间件处理必须位于主流程中段，上游输入、下游输出、内部存储和配置区要分层表达，不能混成同一堆方块。
- 业务泳道型中，阶段标题清晰，主流程方向向下，旁路训练/日志/评测链路要与主流程区分。
- 代码逻辑分层型中，入口、业务逻辑、引擎、核心处理、外部服务要能顺序读通；公共模块只能作为共享能力区。
- 组件/包逻辑型中，包边界、调用主线、配置/刷新链路、说明区要分开表达，不要把说明文字塞进主流程卡片。
- 双流程/状态机型中，两条主流程颜色和边界清晰，每条流程内部自上而下，共享模块放在两条流程下方或独立共享能力区。
- 箭头数量克制，避免大面积交叉；必要时用少量主干箭头表达方向。
- 不允许出现斜向主箭头；主流程箭头必须是垂直直线或直角折线。辅助虚线也尽量正交，不能大面积斜穿页面。
- 所有模块文字应能在框内完整显示，不要溢出或遮挡。
- drawio 中标题、说明、模块卡片、连线不得互相遮挡；容器标题必须位于顶部标题条或独立文本框。
- 入口层、核心处理层内部卡片上方不得出现跨层横线；横向线段只允许放在两个主层级之间的空白带，或放在明确标注的总线位置。
- 在 diagrams.net 中打开时，任意线条都不能压在中文标题、说明文字、模块卡片文字上方；如果做不到，优先减少线条数量，而不是保留完整调用线。
- 部署与运行时信息默认不得出现在主图中；如果出现，必须能说明它与当前代码主流程强相关。
- 业务域和核心模块必须包含可定位代码线索；如果某个域没有代表文件名，说明扫描证据不足并回到仓库继续阅读。代码线索是定位入口，不是完整清单。

## 校验

完成前必须检查：

- 生成文件中没有 `TODO`、`[PROJECT]`、乱码或模板占位符。
- SVG 包含真实 `<svg>` 内容，可以独立打开。
- drawio 包含 `<mxfile`、`<mxGraphModel` 和可编辑的 `mxCell` 元素。
- drawio 不包含 `image;` 或 `data:image` 这类嵌入整图的伪编辑内容。
- SVG 和 drawio 中的核心标题、领域名称、模块名称保持一致。
- 必须执行文案遮挡自检：检查文本容量、容器内重叠、标题/说明/子卡片间距、连线标签是否压住文字。
- 必须执行连线遮挡自检：主链路不得穿过模块标题、说明文字、正文文本；如果穿过，先改为层间总线或减少连线。
- 如果几何自检发现风险，必须修改 SVG/drawio 后再次检查，不能把“可能遮挡”的图交付给用户。
- 如果没有做浏览器视觉检查，要在最终回复中说明。

## 调用链可见性补充规则

生成 SVG 和 drawio 时，调用链路不能只是“不遮挡”，但也不能抢过模块本身。

- 主调用链必须清晰可见：使用中等线宽、适中箭头、纵向直达箭头和短中文标签，不能弱化成背景装饰线，也不能大到成为第一视觉焦点。
- 主调用链可以作为前景线绘制，但必须走层间空白通道且不压住文字；辅助依赖线才作为背景层绘制。
- 如果某条线不能同时满足“清晰可见”和“不遮挡”，优先调整层间距、增加带标签总线或减少线条数量，不要通过超大箭头解决可读性。
- 主调用链必须保持正交：优先垂直向下；需要跨列时先垂直进入层间空白带，再水平移动，再垂直落到目标模块。不要用斜线表达跨列调用。
- SVG 主调用链建议使用 `stroke-width=1.8~2.4`，`markerWidth=10~13`，`markerHeight=7~10`，必要时使用 `stroke-linecap=round`。
- drawio 主调用链建议使用 `strokeWidth=2;endSize=9~11;startSize=7~9;fontSize=10;fontStyle=1;`，并给关键边设置短标签。
- 辅助依赖线建议使用 `strokeWidth=1.2~1.6;dashed=1;opacity=55~70`，避免和主调用链竞争。
- 主调用链至少覆盖三段：入口到核心、核心到出站、出站到底层；每段至少有 1 条清晰箭头或 1 条带标签总线。
- 视觉缩放到 75% 时仍应能看出主调用方向；如果看不清，优先增加标签、调整颜色对比或减少背景干扰，再考虑小幅加粗线条。
- 箭头面积不得明显大于普通模块高度的 35%，避免像大三角块一样压迫画面。
- SVG 和 drawio 中的主调用链必须经过视觉检查；不能只通过 XML 合法性检查。
