# Shipyard — 图纸 → 工单 → 下水

用概要设计、详细设计、任务和验收记录把需求推进到交付。决策、进度及恢复所需信息写入文件；用户指定范围、暂停或改变方向时，以用户意图为准。

## 产物和状态

在当前项目创建 `docs/shipyard/<项目名或需求名>/`（用户指定其他位置时从其指定）：

- `hld.md`：目标、边界、概要设计；统一维护项目阶段、状态、下一步及阶段例外。
- `lld.md`：现行详细设计、行为与接口契约。
- `tasks.md`：任务、清单确认、实施和验证记录、遗留及最终验收。
- `runbook.md`（按需）：存在部署或运行交接需要时，记录配置、操作和恢复步骤。

按阶段创建文件，不预建后续文件。同一事实在上述主要位置维护，其他位置用链接引用；执行结果写入任务记录，不在设计正文重复维护。任务尚未建立时，前提核验的证据记在相关设计点，后续任务引用即可，无需提前创建任务文件。每次决策、变更或完成任务后立即更新受影响内容。编号各自在文档内连续分配、不回收；废弃项保留编号和原因，不参与进度分母、门禁或覆盖检查。

### 排版与回链

- 按模块或主题用 `## A. <主题>`、`## B. <主题>` 分组，设计点用 `### [ ] 4. <业务名称>` 或 `### [x] 4. <业务名称>`，任务标题用同样结构及 T 编号，使支持目录的查看器可直接定位单项并展示状态。编号在同一文件内跨组连续，不按组重新从 1 开始；标题简短，回链和方法、路径等细节放正文。一个设计点聚焦一个可独立理解和追踪的主题；涉及多个独立决策或大段不同内容时拆分，避免为了排版机械拆分。已有编号不重排；需要拆分时保留原项及其历史，新增独立点分配新编号并更新回链。
- 在每个设计点或任务标题前单独放置稳定锚点，并与标题间留一个空行：`<a id="hld-2"></a>`、`<a id="lld-3"></a>`、`<a id="task-t-1"></a>`；子任务如 T-3a 使用 `task-t-3a`。锚点只由文档类型和编号决定，不受标题、勾选状态变化影响。同一文件内 ID 唯一，废弃项也保留原锚点。
- 使用相对 Markdown 链接回链，如 `[hld #2](hld.md#hld-2)`、`[lld #3](lld.md#lld-3)`、`[T-1](tasks.md#task-t-1)`；多个目标逐个链接，不用范围代替具体链接。只链接已经存在的目标；跨目录时按源文件位置计算相对路径。设计点回链放在标题下的独立列表项，保持目录标题简洁。
- 旧文档可能只有纯文本回链或缺少锚点。恢复时先识别原编号和状态；在本次编辑涉及的现有目标上补锚点并更新相关链接，不重写未涉及文档，也不把格式迁移当作设计确认。若目标尚不存在或无法修改，保留可识别的纯文本引用并说明，避免生成失效链接。实际跳转取决于查看器对相对链接和 HTML 锚点的支持。
- 适合对照的信息使用简短列表或表格；请求、响应和配置示例使用标注语言的代码块。长段落按主题拆开，避免把契约、故障处理和验证结果混在同一条中。
- 正文只保留一个一级标题；状态用简短的两列表格，下一步单独突出。目录以项目、模块、编号条目三层为主；条目内部默认用独立加粗标签，如“要确认”“建议”“结论”“依据”“请求参数”，标签后留空行再写短列表、表格或示例，避免目录充满重复的小节。确需单独导航的长内容才使用四级标题。模板使用说明、占位提示和不适用的示例区在生成时移除。
- 标准标题作为目录来源；只有需要对照方法、路径等信息时，才另加 LLD 接口总览并链接实际条目，不手工重复整份目录。字段表仅放短约束，复杂规则放在表后；示例放在表外。以清晰层级、留白和统一格式改善阅读，不依赖彩色 HTML、装饰图标或折叠关键契约。

`hld.md` 状态区记录当前阶段（概要设计 / 详细设计 / 任务拆解 / 实施 / 最终验收 / 已完成）、项目状态（进行中 / 暂停 / 阻塞 / 已完成 / 已完成（带遗留））、下一步、阶段例外及依据；其他文档引用此处，不另维护项目阶段。设计文档用“设计进度”统计用户确认和有依据的自主决定；任务清单记录待确认 / 已确认、确认依据和日期，以及验收完成数。不要把生成清单当作用户确认。勾选项是各文档有效项计数的依据；代码完成但验收未通过的任务保持未勾选，可简记“实现完成，待环境验证”，不另建一套代码完成计数。

## 阶段与门禁

| 阶段 | 进入和退出条件 |
|------|----------------|
| 概要设计 | 明确需求后开始；有效待确认设计点解决后进入详细设计 |
| 详细设计 | 概要设计门禁通过；有效待确认设计点解决后进入任务拆解 |
| 任务拆解 | 详细设计门禁通过；用户明确确认清单后进入实施 |
| 实施 | 清单已确认，或用户明确授权跳过任务拆解；完成约定实现和任务级验证后进入最终验收；预先安排在最终验收的联调等任务可待执行 |
| 最终验收 | 核对目标和整体验证，记录结果与遗留项后完成 |

用户可以指定只做到某阶段或暂停，记录下一步并停止。用户明确要求跳过任务拆解直接实施时，在 `hld.md` 记录授权、范围和依据；概要与详细设计的门禁仍适用。创建 `tasks.md` 作为简要实施与验证日志，标明“任务拆解：用户授权跳过”，无需补做清单确认，按模板记录每项实际改动、依据、验证结果、阻塞和下一步；约定范围完成并通过最终验收后方可结束。若用户也明确要求跳过设计门禁或从已有设计直接开始，记录授权与适用范围，以现有材料为依据推进；存在会影响安全或不可逆后果的关键未知时先澄清。不得将默认沉默或模糊措辞当作跳过授权。

## 设计点和确认

先检查用户提供的信息及相关仓库代码、约定和约束，提炼目的、成功标准、使用方式、前提和非目标。事实注明来源；缺失但可合理推断的常规选择记录假设、依据及影响，按授权范围直接决定并标记 `[x]`。需要用户决定的点保留 `[ ]`：例如目标或范围不明、影响外部契约与兼容性、重大成本或难以撤销的选择；每点附建议和理由，按关联问题批量询问。只有明确回答或授权才记为用户确认，部分回答先落盘已解决部分。用户推翻结论时记录新结论并检查下游影响。

设计复杂度结合操作频率、并发规模、失败后果及人工恢复是否可接受来决定。引入额外协调、持久化或恢复机制时，说明其解决的具体问题，优先复用现有能力。用户已明确选择的简化及风险边界写入结论和依据；后续用户改变要求或新证据改变其适用前提时再重新评估。

设计点 `[x]` 表示方案已决定，不代表依赖或环境能力已验证。会影响方案可行性或成功标准的未验证前提，附在相关设计点下：当前证据、验证动作与预期结果、最迟验证阶段、失败影响及处理。优先验证可能推翻方案的前提；暂不可验证时写明可继续的范围和必须等待的交付结论。任务建立后链接承接任务，后续验证结果统一写入任务记录；未验证前提不得作为已证实事实通过所依赖的验收。

```markdown
### [ ] 4. 聚合接口

**要确认**

- 进度更新使用轮询还是 SSE。

**建议**

- 使用轮询，沿用现有客户端，第一版实现较简单。

### [x] 4. 聚合接口

**结论**

- 第一版使用轮询，接口为 `GET /api/apps/:appId/releases`。

**依据**

- 用户确认 / 仓库既有约定（注明来源）。
```

上例表示同一设计点确认前后的两种状态，生成正文只保留当前版本；部分问题仍未解决时保持 `[ ]`，分别列出已确定结论与剩余问题，不因排版迁移改变确认状态。

## 阶段 1：概要设计

读 [`references/hld-template.md`](references/hld-template.md)。按需求描述模块职责和关系、接口或交互边界、数据模型概览、外部依赖及契约；不适用的类别注明原因。目标是让开发者理解系统边界与连接，字段级细节留给详细设计。

## 阶段 2：详细设计

读 [`references/lld-template.md`](references/lld-template.md)，展开适用的设计点并回链概要设计。新增超出概要边界的设计先更新概要设计。按需要覆盖接口 schema、错误处理、存储与索引、关键流程、状态及恢复、并发与幂等、异常、兼容和迁移；不适用项注明原因。结论具体到开发和验证所需的程度。

新增或修改 HTTP 接口时，再读 [`references/api-template.md`](references/api-template.md)。默认一个“请求方法 + 路径”对应一个独立编号设计点，CRUD 各接口分别展开；同一接口的参数、响应、错误和规则写在该点内。公共鉴权、响应包装、分页等约定集中维护并回链，各接口仍给出自身完整请求和成功响应示例。沿用项目接口风格，不为符合模板改造既有 POST 查询或响应结构；非 HTTP 交互按实际协议调整。

接口独立编号用于定位和追踪，不代表逐个向用户确认或一接口一任务。沿用已确认约定的接口可自主决定并写依据；只有未解决的重要决策保留待确认，相关问题批量询问。任务按交付物关联多个接口点；扩展既有文档时保留原编号，需拆分的旧项保留历史和新点链接。

## 阶段 3：任务拆解

读 [`references/tasks-template.md`](references/tasks-template.md)。按可独立验收的交付物拆任务，优先可独立提交；强耦合改动允许组合交付和联合验收。代码及本地验证、环境联调具有不同等待条件且可独立验收时分开安排；预定在最终验收执行的任务注明阶段。依赖写明实际就绪条件，如“接口契约已确定”或“代码及本地验证完成”，避免把尚待联调的整个任务当作已完成依赖。拆分任务不得遗漏原验收条件，也不得为提高完成率降低标准。

每项写编号、回链、范围、依赖和验收；检查每个有效 LLD 点及关键前提验证均有任务承接，无法关联的点说明原因或补拆。若用户明确授权跳过设计门禁且不存在 LLD，任务改为回链 HLD 或已有材料并注明依据；覆盖检查以现有有效设计和授权范围为准。清单整体交用户确认，确认依据落盘后实施。

## 阶段 4：实施与变更

按依赖的就绪条件选择可开始的未完成任务，简要报告后实施；完成验收后记录验证方式、结果和必要证据，再勾选。证据注明验证日期、适用代码版本或工作区范围及环境，说明关键场景和相关跳过项的影响，不能只用测试总数代替覆盖情况。提交需遵循用户授权，可使用 `/git-commit`，不把任务完成等同于必须提交。验证失败或条件未具备时记录阻塞和下一步，不勾选。

实施中发现偏差时先判断影响：

- **局部补充**：不改变已确认的对外行为、范围、兼容性或其他重要约束，按现有授权决定并更新相关文档，记录依据；继续实施。
- **影响已确认决策**：先记录变更及建议，检查受影响的 HLD、LLD、任务和已完成代码。需要用户决策的点重新确认；标记受影响任务待返工或待复验，更新依赖和验收，再继续。用户已明确授权的选择记录授权依据。

变更已获授权或可自主决定后，在本次工作中完成以下同步，才能将其记为已落实：

1. 将现行结论写回原 HLD/LLD 设计点；保留编号，在原项下简记替代日期、原因和依据。新增独立决策才分配新编号，废弃项标明原因。不得仅在文件顶部追加说明并要求读者自行拼合历史。
2. 更新受影响任务的范围、依赖和验收；撤销被变更失效的完成勾选，保留旧证据及其适用范围，记录返工或复验。已删除的能力不再作为现行验收条件，必要的风险边界和替代验证仍需保留。
3. 核对当前实现与现行设计，更新 HLD 状态及下一步、各文档计数和相关链接；移除指向已删除文件的可点击链接，历史可保留文字说明。

尚未实现或复验的部分明确留待办。任务的验证结果不能代替设计修订；无法更新相关文件时说明原因和待同步内容，不宣称变更已全部落实。

## 最终验收

对照目标、成功标准和非目标，执行适用的跨任务集成或端到端验证，检查必要的兼容、迁移及回滚准备。记录每项验证的方式、结果、未验证原因和遗留问题；不能验证的内容不伪称通过。涉及发布时记录发布准备和所需授权，按用户明确授权执行部署及上线验证；没有授权时停在可交付状态并说明。未验证项或遗留问题影响成功标准时，保持阻塞或进行中并记录下一步；不影响约定交付标准时，可记录“已完成（带遗留）”及其影响。用户要求上线但尚无授权时，保持最终验收阶段、项目状态为阻塞，写明待授权及后续动作。完成实施不自动表示已上线。

重要未验证项逐项关联任务或成功标准，写明所需条件、检查动作、预期结果、当前阻塞及下一步；不要只写“待环境验证”。同一验证在任务记录中维护，最终验收引用结果。需要运行交接时，runbook 的人工恢复步骤应说明核对对象、处理路径及允许恢复的条件；尚未确定或未演练的步骤明确标注。

## 恢复会话

用户说“继续 <项目名>”或给出设计目录时：

1. 先定位目录。目录不存在才作为新项目；目录存在但缺少后续阶段文件可能是正常进度，明确记录授权跳过的阶段文件缺失属于例外；缺少按状态应已存在的文件则报告异常并依据现有证据恢复，不覆盖已有文件。
2. 读取 HLD 状态、阶段例外、清单确认依据及有效项；以条目实际状态重算计数，排除废弃项。旧文档重复记录阶段或用顶部变更覆盖正文时，结合确认记录和实现证据核实后按变更同步规则修正，不单凭较新的时间戳决定。确认依据缺失时不得推定清单已确认。
3. 核对已完成任务的验证记录与当前代码/工作区，识别未提交改动、变更、关键前提和阻塞；不擅自覆盖。区分尚未实现与已实现待验证，按具体就绪条件和下一步继续；信息冲突无法安全判断时提出带建议的澄清。
4. 汇报阶段、进度、阻塞与下一步。明确暂停或用户指定停止的状态不自动越过。

对话中简要报告进度与待决事项，设计内容写入文档，不重复整份文件。
