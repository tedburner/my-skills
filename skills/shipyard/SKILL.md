# Shipyard — 图纸 → 工单 → 下水

用设计与任务记录把需求推进到交付，使核心决策、契约、进度和未验证风险一目了然。用户指定范围、暂停或改变方向时，以用户意图为准。

## 模式与产物

在当前项目创建 `docs/shipyard/<项目名或需求名>/`（用户指定其他位置时从其指定），按需求复杂度二选一：

### 1. 轻量模式（默认优先）

适用：简单 CRUD、单一模块扩展、少量字段或接口增量调整、无跨模块复杂状态机。

- `design.md`：合并目标边界、决策点、接口契约或字段改动，同时作为项目阶段与状态的唯一锚点。
- `tasks.md`：任务拆解、验证记录、遗留与最终验收。
- 读 [`references/design-template.md`](references/design-template.md) 和 [`references/tasks-template.md`](references/tasks-template.md)。无高风险待决点时，可在同一轮展示精简设计与任务清单，用户确认后直接实施。
- 若实施中范围明显扩大或出现复杂跨模块协同，可在保留原有条目编号的前提下按需拆出 `lld.md`（或继续在 `design.md` 分区展开）并更新状态锚点。

### 2. 完整模式

适用：跨模块/多服务协同、复杂并发或状态机、多方接口对接、需要先评审概要边界再展开详设。

- `hld.md`：目标、边界、概要设计；统一维护项目阶段、状态、下一步及阶段例外。
- `lld.md`：现行详细设计、行为与接口契约。
- `tasks.md`：任务、清单确认、实施和验证记录、遗留及最终验收。
- `runbook.md`（按需）：存在部署、定时调度或运维人工恢复交接需要时记录。

按阶段创建文件，不预建后续文件。同一事实只在主要位置维护，其他位置用链接引用。仓库 `AGENTS.md` 或全局规范已固化的构建命令、鉴权方式、响应包装、字段命名和读写策略等，**在文档中一句话引用即可，正文只写本需求的差异、例外与特有契约**。编号各自在文档内连续分配、不回收；废弃项保留编号和原因，不参与进度分母、门禁或覆盖检查。

### 排版与回链

- 按模块或主题用 `## A. <主题>`、`## B. <主题>` 分组，设计点用 `### [ ] 4. <业务名称>` 或 `### [x] 4. <业务名称>`，任务标题用同样结构及 `T-N` 编号，使目录可直接定位单项并展示状态。编号同一文件内跨组连续，标题保持简短（方法、路径、回链和细节放正文）。
- 在每个设计点或任务标题前单独放置稳定锚点并留一个空行：`<a id="design-2"></a>`、`<a id="hld-2"></a>`、`<a id="lld-3"></a>`、`<a id="task-t-1"></a>`（子任务如 `task-t-3a`）。同一文件内 ID 唯一，废弃项也保留原锚点。
- 使用相对 Markdown 链接回链，如 `[design #2](design.md#design-2)`、`[hld #2](hld.md#hld-2)`、`[lld #3](lld.md#lld-3)`、`[T-1](tasks.md#task-t-1)`；同文件内直接用 `#design-2`；多个目标逐个链接，不链向不存在或已删除的文件。
- 恢复旧文档时先识别原编号和状态，仅在本次涉及的现有目标上补锚点并清理失效链接，不重写未涉及文档。
- 正文只保留一个一级标题，状态用简短两列表格，下一步单独突出。条目内部用独立加粗标签（如“要确认”“建议”“结论”“依据”“入参”“出参”），标签后留空行再写短列表、表格或示例，保持目录干净（最多三层）。模板占位提示与不适用的示例区在生成时移除。

### 状态与归档

状态锚点文件（轻量模式 `design.md` / 完整模式 `hld.md`）统一记录：
- **当前阶段**：`设计`（轻量）/ `概要设计` / `详细设计` / `任务拆解` / `实施` / `最终验收` / `已完成` / `已归档`
- **项目状态**：`进行中` / `暂停` / `阻塞` / `待环境联调` / `已完成` / `已完成（带遗留）` / `已归档（已取代）`

其他文档状态区直接引用状态锚点，不另起或自造阶段词。代码完成但尚未通过本地验收的任务保持 `[ ]`，不另建代码完成计数。

**方案被取代或废弃时**：将旧目录状态锚点更新为 `当前阶段：已归档`、`项目状态：已归档（由 [<新方案>](...) 取代）`，冻结后续进度分母与门禁，清理旧目录中指向已删文件的失效链接。**后续迭代修改先前模块行为时**，只在新需求目录写现行设计并注明替代旧目录的对应条款，不在旧目录正文打局部补丁导致状态分裂。

## 阶段与门禁

| 阶段 | 进入和退出条件 |
|---|---|
| 设计（轻量） | 明确需求后开始；待确认点解决且任务清单确认后进入实施 |
| 概要设计（完整） | 明确需求后开始；有效待确认设计点解决后进入详细设计 |
| 详细设计（完整） | 概要设计门禁通过；有效待确认设计点解决后进入任务拆解 |
| 任务拆解（完整） | 详细设计门禁通过；用户明确确认清单后进入实施 |
| 实施 | 清单已确认（或用户明确授权跳过拆解）；完成本地实现与任务级验证后进入最终验收 |
| 最终验收 | 核对目标、本地整体验证及未验证/外部联调项登记后收敛状态 |

- 用户说“下一步”“开始实现编码”等推进指令时：若有效待确认设计点已无未决项，可记为进入下一阶段或实施的授权依据；若仍存在会影响外部契约、数据安全或不可逆后果的关键待确认点，须先澄清后再实施，不得将沉默当作授权。
- **交互式确认优先**：当存在明确离散选项的 `[ ]` 设计点（如二选一/三选一技术方案）或进入阶段门禁确认（如“确认清单并开始实施 / 继续调整 / 暂停”）时，若当前环境提供交互式单选/多选工具（如 `ask_question`、`AskUserQuestion`、`request_user_input` 等），优先在展示简要摘要后直接调用选项组件供用户点击确认；无可用组件或问题偏开放式时，再在正文列出清晰编号供文字回复。
- 用户明确授权跳过任务拆解或直接基于已有设计/代码补档时，在状态锚点记录授权、范围和依据；`tasks.md` 仍需记录实际改动、验证结果与未验证阻塞。

## 设计点和确认

先检查用户输入及相关仓库代码、约定和约束，提炼目的、成功标准、使用方式和非目标。事实注明来源；常规技术选择记录假设、依据并直接标记 `[x]`。真正需要用户决策的点保留 `[ ]`（如范围不明、外部契约变更、高成本或不可逆选择），每点附简短“要确认 / 建议”按关联问题批量询问。

```markdown
### [ ] 4. 聚合接口

**要确认**

- `GET /api/apps/:appId/releases`
- 进度更新使用轮询还是 SSE。

**建议**

- 第一版用 2–3 秒轮询，沿用现有客户端，实现更简单。
```

设计点 `[x]` 仅表示方案已决定，不代表环境或依赖已验证。会影响方案可行性的关键未验证前提，在相关设计点下写明当前证据、验证动作、最迟验证阶段及失败处理；任务建立后链接承接任务，不在多处重复维护验证结果。

## 阶段设计规范

- **概要设计（完整模式）**：读 [`references/hld-template.md`](references/hld-template.md)，聚焦模块职责边界、接口概览、数据模型概览与外部依赖，字段级细节留给 LLD。
- **详细设计（完整模式） / 合并设计（轻量模式）**：完整模式读 [`references/lld-template.md`](references/lld-template.md)，轻量模式读 [`references/design-template.md`](references/design-template.md)。按需要覆盖存储与索引、核心流程、状态并发及异常边界，不适用项一句话注明即可。
- **HTTP 接口按复杂度三档编写**：读 [`references/api-template.md`](references/api-template.md)，不搞一刀切：
  1. **简单 CRUD / 常规内部接口（默认）**：使用「紧凑接口卡」（方法与路径、入参简表、出参结构或简短 JSON 示例、关键校验与异常）；同模块共享 VO 时集中定义一次，后续接口直接引用。
  2. **存量接口增量修改**：只写方法与路径、本次新增/修改/废弃字段表、局部差异示例与兼容边界，不重抄未改动的存量字段。
  3. **复杂协议 / 对外回调 / 高并发状态机接口**：按需展开完整接口模板（请求头、完整 HTTP 示例、逐状态错误码、幂等恢复规则）。
  - 若项目使用权威接口平台（如 YAPI/OpenAPI）维护全量 Schema，设计正文聚焦契约差异、核心示例与平台接口 ID 索引，不手工重复维护两份全量字段表。

## 任务拆解：本地交付与外部联调解耦

读 [`references/tasks-template.md`](references/tasks-template.md)，按可独立验收的交付物拆分任务，并严格区分两类验收条件：

1. **本地交付任务（代码、单测、隔离集成测试、接口平台 API 写入）**：验收条件只绑定**在当前工作区或本地隔离环境即可完成核验**的标准。**禁止将目标环境部署、真实测试/线上库权限、跨团队联调、DBA 建索引或人工 UI 预览设为本地编码任务的前置依赖或验收卡点**，防止级联出现 `0 / N` 阻塞。
2. **外部与环境任务（目标环境联调、真实并发/索引核验、人工页面确认、发布）**：统一单独拆为后置任务，标注 `阶段：最终验收（外部依赖）`；进入最终验收不代表这些外部任务已通过。

任务按模块/主题分组；设计点较多时可附可选的 `设计覆盖核对` 表，确保有效设计点与关键前提均有承接。

## 实施、变更与验证记录

按依赖就绪条件推进未完成任务，完成后记录验证证据再勾选 `[x]`：注明验证日期、命令、适用范围及关键场景，不以编译通过或 `UP-TO-DATE` 缓存构建替代实际测试运行。提交需遵循用户授权（可使用 `/git-commit`）。

**发现偏差或引入外部补充方案时**：
- 局部补充不改变对外契约和重要边界时，更新对应设计点并继续；影响已确认决策时，先重新确认并标注受影响任务待返工/复验。
- 将现行结论直接写回原设计点并简记替代日期与原因；**不得只在文件顶部堆砌说明**。
- 中途若通过其他文档或工具产出补充设计（如外部 spec），纳入 Shipyard 时**必须回写现行设计点并拆为新的 `T-N` 任务**，**禁止在 `tasks.md` 末尾 `最终验收` 之下贴无编号追加段落**。

**验证记录保持紧凑（现行态优先）**：同一任务经过多轮修复与复验后，以最新一轮的有效范围、环境、命令与通过/未通过结论为主体覆盖或更新；已修复的历史失败过程压缩为一句话或移除，不在单个条目中无限制堆砌多轮流水账。

## 最终验收

对照目标、成功标准和非目标核对整体验证，记录未验证项和遗留问题，不能验证的内容不伪称通过：
- **本地交付闭环收敛**：当用户授权范围仅限本地开发与本地测试（不包含部署、目标环境联调或外部验收）时，只要全部本地交付任务已 `[x]` 通过，且所有外部任务与未验证风险均已在最终验收中关联对应 `T-N` 写明条件、动作与影响，即可结束 `实施` 进入 `最终验收`，并标记项目状态为 **`待环境联调`** 或 **`已完成（带遗留）`**（说明待外部推进的范围与下一步），无需永久停在 `实施`。
- 需要部署或上线而尚无授权时，保持 `最终验收` 阶段并写明待授权项。需要 `runbook.md` 时，写明核对对象、处理路径及恢复条件，未演练步骤明确标注。

## 恢复会话

用户说“继续 <项目名>”或给出设计目录时：
1. 定位目录，识别采用轻量模式（`design.md` + `tasks.md`）还是完整模式（`hld.md` + `lld.md` + `tasks.md`）。若状态为 `已归档`，直接汇报其取代去向，不自动在归档目录继续开发。
2. 读取状态锚点、阶段例外、清单确认依据与有效项，按实际 `[x]`/`[ ]` 重算计数（排除废弃项）。
3. 核对工作区改动与已完成任务记录，区分未实现、已实现待验证与外部联调阻塞，简要汇报当前阶段、进度、阻塞与下一步后继续。

## 落盘前 4 项自检

每次创建或更新 Shipyard 文档收尾前快速核对：
1. **状态唯一且规范**：阶段与状态使用标准枚举，除状态锚点外不另建阶段定义。
2. **本地与外部解耦**：本地交付任务未将外部环境或人工 UI 预览作为前置卡点。
3. **正文紧凑去重**：未复读仓库 `AGENTS.md` 通用约定；验证记录聚焦现行结果；无文末无编号追加段。
4. **链接与计数准确**：无失效相对链接（已删文件链接已清除），进度数字与有效勾选项一致。

对话中简要汇报进度与待决事项，设计内容写入文档，不重复整份文件。
