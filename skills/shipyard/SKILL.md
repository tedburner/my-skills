# Shipyard — 图纸 → 工单 → 下水

像造船一样做开发：先画图纸（概要设计、详细设计），再开工单（任务拆解），最后下水（实施）。

核心产物不是对话里的完美回答，而是**三份落盘的文档**。状态全部存在文件里——任何只存在于对话中的决策等于不存在，这是跨会话恢复能力的根基。

---

## 总原则

- **状态落盘**：每确认一个点，立即写回文件并打 `[x]`；对话结束，进度不能丢。
- **Gate 是硬规则**：上一阶段设计点未全部 `[x]`，不写下一阶段的文件。宁可多确认一轮，不带病过关。
- **给建议，不抛问题**：每个待确认的点必须附推荐方案和理由，用户可以否，但不能让用户面对裸问题。
- **结论具体到可实施**：接口写全 path/参数/错误码，表写全字段。"到时候再说"不算结论。
- **文档是唯一事实源**：实施阶段发现文档和代码不一致，先归位（改文档或改代码）再继续。
- **流程为人服务**：用户想停在某个阶段、只做概要设计、或跳过任务直接实施，都允许；gate 只在"想往前走"时生效。

---

## 产物与位置

在用户当前开发的项目下创建（用户指定了其他位置则听用户的）。目录名用项目名或需求名，以当前设计的粒度为准：

```
docs/shipyard/<项目名或需求名>/
├── hld.md      # 概要设计（图纸）：架构、模块、接口清单、数据模型
├── lld.md      # 详细设计：每个设计点的 schema、表结构、状态机、异常分支
└── tasks.md    # 工单：回链 lld 编号的任务清单
```

## 四个阶段

| 阶段 | 产物 | 进入条件 | 退出条件（gate） |
|------|------|----------|------------------|
| 1 概要设计 | hld.md | 有可描述的需求 | 设计点全部 `[x]` |
| 2 详细设计 | lld.md | hld 全部 `[x]` | 设计点全部 `[x]` |
| 3 任务拆解 | tasks.md | lld 全部 `[x]` | 用户确认整份清单 |
| 4 实施 | 代码 + tasks.md 打勾 | tasks 已确认 | 全部任务 `[x]` |

---

## 设计点与确认协议

hld 和 lld 都由**设计点**组成：全局连续编号（`#1`、`#2`……不随章节重置），按主题域分节（A/B/C/D…）。设计点是最小确认单元。编号一经分配不回收，作废的点标注废弃并注明原因，保持回链稳定。

未确认 / 已确认两种形态：

```markdown
### [ ] 4. 聚合接口
- 要确认：进度更新用轮询还是 SSE
- 建议：轮询。返回结构不变，前端改动最小；返回体预留字段，后续可平滑升 SSE

### [x] 4. 聚合接口
- 结论：GET /api/apps/:appId/releases，第一版轮询；返回体含阶段、活动原因、
  测试/生产版本与访问地址，预留 SSE 升级空间
```

确认协议：

- **批量抛点**：每轮列出当前章节所有 `要确认` 的问题与各自建议，等用户一次回复；不逐点挤牙膏。
- **部分回答**：用户只拍板了部分，先把拍板的写回文件打 `[x]`，剩余点下一轮再抛。
- **推翻结论**：用户推翻已确认的点，改写结论、回退 `[x]`，并检查下游设计点是否受牵连——受牵连的一并回退并向用户说明。
- 阶段 3/4 不逐点确认：tasks 清单确认一次，实施过程直接推进。

---

## 阶段 1：概要设计

先澄清再动笔：从用户输入提炼 目的、已确认的前提（约束、已定技术栈）、使用方式、非目标；提不出来的直接问，不靠猜。

然后读 [`references/hld-template.md`](references/hld-template.md)，生成 hld.md。设计点须覆盖：模块划分与职责边界、接口清单、数据模型概览、外部依赖与契约。

合格标准：换一个开发者只读 hld.md，能说清系统分几块、块之间怎么连——不需要懂任何字段级细节，字段是 lld 的事。

## 阶段 2：详细设计

读 [`references/lld-template.md`](references/lld-template.md)，按 hld 的模块逐个展开。每个设计点必须回链 hld 编号；冒出无回链的新点，先回 hld 补设计再展开。

须覆盖：API 请求/响应 schema 与错误码、表结构与索引、关键流程时序、状态机、幂等与状态恢复、异常与边界、兼容与迁移。

合格标准：开发者读完一个设计点就能写代码，不需要再问"这个字段什么类型、这个错误怎么返回"。

## 阶段 3：任务拆解

读 [`references/tasks-template.md`](references/tasks-template.md)。

- **粒度**：一个任务 = 一次可独立提交、可独立验证的改动。切不到这个粒度就继续拆。
- 每个任务：编号、回链 lld 设计点、范围、验收标准。没有任何任务回链的 lld 设计点，要么漏拆，要么设计多余——两头都要查。
- 排出依赖顺序后，整份清单向用户确认一次。

## 阶段 4：实施

逐任务推进：

1. 取第一个未完成任务，向用户报「开始 T-N」。
2. 实施并验证，达到验收标准为止。
3. 在 tasks.md 打勾（可备注 commit hash），提交时可走 `/git-commit`。
4. 重复直到清零；全部完成后给出交付小结（做了什么、改了哪些文档、遗留问题）。

**防漂移规则**：实施中发现设计缺口、设计有误、或有更好的方案——停下手头的编码，先把变更写回 hld/lld 作为新设计点（未确认的走一遍确认协议），再继续实施。禁止"代码里顺手改了，文档不知道"。

---

## 恢复会话

用户说「继续 <项目名>」或给出设计目录时：

1. 读三份文件的状态行和 `[x]` 分布，判断当前阶段与进度。
2. 一句话汇报：处于阶段 N、进度 x/y、下一个动作是什么。
3. 从断点继续。文件不存在则视为新项目，确认项目名后从阶段 1 开始。

---

## 输出风格

- 进度一行汇报：`阶段 2 详细设计 · 12/19 已确认 · 下一批待确认：#13-#15`。
- 待确认点列清单：问题 + 建议各一句，不写长篇论证。
- 设计内容写进文档，对话里只给摘要和待确认点；不把整份文档复读到对话里。
